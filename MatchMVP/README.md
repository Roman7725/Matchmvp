# Match MVP — минимальное приложение для первого ивента

Реальный BLE-мэтчинг: телефоны обнаруживают друг друга через Bluetooth,
анонимно лайкают, при взаимности — раскрывается никнейм.

## Архитектура (коротко)

- **BLE (на телефоне)** — только для одной задачи: понять, кто физически
  рядом, через анонимный ротирующийся ID. Никаких имён, никаких физических
  описаний в эфире.
- **Firebase Firestore + Cloud Function (на сервере)** — вся логика лайков
  и мэтчинга. Это принципиально: клиент НЕ может прочитать чужие лайки,
  даже через отладку в браузере/приложении — лайки проверяет и сверяет
  только серверная функция.
- **Firebase Anonymous Auth** — у каждого участника есть анонимный,
  но настоящий проверяемый uid, без сбора личных данных при входе.

## Что нужно сделать перед первым запуском

### 1. Создать проект Firebase
1. Зайти на https://console.firebase.google.com → Create Project
2. Включить **Authentication → Anonymous** (Sign-in method)
3. Включить **Firestore Database** (Production mode)
4. Добавить Android-приложение в проект, package name: `com.matchmvp.app`
5. Скачать `google-services.json` и положить его в `app/` (рядом с `build.gradle.kts`)

### 2. Задеплоить правила безопасности Firestore
```bash
firebase deploy --only firestore:rules
```
(файл `firestore.rules` уже в этом проекте — см. ниже)

### 3. Задеплоить Cloud Function (проверка мэтчей)
```bash
cd functions
npm install
firebase deploy --only functions
```

### 4. Открыть `app/` в Android Studio, собрать и установить на 2-3 телефона
- Минимум Android 8.0 (API 26) — там появился нормальный BLE advertising API
- На каждом устройстве при первом запуске нужно разрешить Bluetooth и
  геолокацию (Android требует permission на геолокацию для BLE-сканирования,
  это ограничение самой ОС, а не наше — реальных координат приложение не
  использует и не хранит)

### 5. Перед ивентом — задать код мероприятия
В `EVENT_CODE` (см. `MainActivity.kt`) впиши код своего пилотного ивента,
например `"campus-party-2026"`. Все участники увидят только тех, кто зашёл
с тем же кодом.

## Как это работает для пользователя

1. Открыть приложение → ввести никнейм и номер телефона → подтвердить 18+
   (номер хранится в приватной, недоступной другим записи до момента,
   пока ты сам не решишь его раскрыть)
2. Приложение начинает (а) транслировать через BLE анонимный ID
   и (б) сканировать эфир в поиске таких же ID рядом
3. На экране — список анонимных аватаров (Лис, Медведь, Сова...),
   которые физически рядом прямо сейчас
4. Тихий лайк — без уведомления другой стороне
5. Если лайк взаимный — Cloud Function на сервере это обнаруживает
   и создаёт "матч", который видят оба участника
6. По кнопке — каждый по отдельности решает показать свой номер
   телефона второй стороне (адрес НЕ раскрывается никогда — это
   осознанное архитектурное решение, см. секцию про приватность)

## Значок сообщества (опционально)

Добавлена настройка при входе: "Показывать значок сообщества". По умолчанию
выключена. Ключевой принцип приватности: **значок другого человека виден
тебе только если у тебя самого он тоже включён** — это гарантируется не
только клиентским кодом, но и правилами безопасности на сервере
(`firestore.rules`, коллекция `community`), которые физически не отдадут
эти данные никому, у кого свой флаг выключен. Если у тебя флаг выключен —
приложение даже не пытается запрашивать чужие значки, чтобы не создавать
лишний сигнал в принципе.

## Баги, найденные при первом реальном запуске (спасибо тестеру!)

При первой попытке собрать и запустить проект нашлись ещё несколько
реальных проблем, которые не всплыли при чтении кода — только на
живом устройстве:

7. **Конфликт тем оформления** — манифест использовал системную тему
   Android, а библиотека AppCompat (подключённая в build.gradle) этого
   не терпит и крашит приложение при запуске. Исправлено: добавлена
   отдельная тема `Theme.MatchMVP`, унаследованная от AppCompat
   (`app/src/main/res/values/styles.xml`).
8. **Крэш из-за аппаратного ускорения** на некоторых чипсетах.
   Исправлено: `android:hardwareAccelerated="false"` в манифесте.
9. **ZIP открывался не тем приложением** — это не баг кода, а настройка
   телефона (нужен архиватор вроде ZArchiver, а не сканер документов).

## Как смотреть крэши без Android Studio (Crashlytics)

Раз ты собираешь через GitHub Actions, а не через Android Studio — тебе
не нужен Logcat. Вместо него подключён **Firebase Crashlytics**: он сам
ловит любой крэш приложения и присылает отчёт прямо в Firebase Console
(обычный сайт в браузере).

### Как включить (один раз)
1. Зайди в свой проект на console.firebase.google.com
2. В меню слева найди **Crashlytics** (в разделе "Release & Monitor")
3. Нажми "Enable Crashlytics" — больше ничего настраивать не нужно,
   всё уже подключено в коде

### Как посмотреть крэш
1. Собери и установи приложение как обычно (через GitHub Actions → скачать APK)
2. Если приложение крашится — просто открой его снова один раз (это
   отправляет отчёт о прошлом крэше на сервер)
3. Вернись в Firebase Console → Crashlytics — там появится отчёт с
   точным местом и причиной ошибки в коде (может занять несколько минут)

Это удобнее, чем ADB/Logcat, именно для твоего случая — не нужен
компьютер с Android Studio, только браузер.

## Многоязычность (RU / EN / FR / DE)

Интерфейс теперь на четырёх языках — переключается автоматически по
системному языку телефона. Все тексты вынесены в `strings.xml`

зашито в коде намертво.

## Список исправленных багов (проверка перед публикацией)

Перед первой публикацией код был проверен, и исправлены следующие реальные проблемы:

1. **Лайки уходили не на того человека** — анонимный Bluetooth-ID использовался
   напрямую как ID пользователя в базе, хотя это разные вещи. Мэтчи никогда
   бы не сработали. Исправлено: добавлена серверная привязка anonymousId → uid.
2. **BLE-реклама превышала лимит пакета** (31 байт) и, скорее всего, не
   запустилась бы на реальных телефонах. Исправлено: убран дублирующий
   список UUID, сокращён payload.
3. **Разрешения на Bluetooth не запрашивались корректно на Android 8-11** —
   пользователь мог навсегда застрять на экране "нужны разрешения".
   Исправлено: разные наборы разрешений для старых и новых версий Android.
4. **Мигающие аватары** — аватар назначался заново случайно при каждом
   сигнале от одного и того же человека. Исправлено: аватар закрепляется
   один раз за анонимным ID.
5. **Лаги интерфейса** от слишком частого обновления списка при частых
   BLE-сигналах. Исправлено: обновление экрана не чаще раза в секунду.
6. **Утечка "слушателей" Firestore и разряд батареи** при повторных заходах
   в приложение. Исправлено: явная отписка при закрытии экрана.

## Как собрать без установки Android Studio (сборка в облаке)

Если твой компьютер слабый — можно собирать `.apk`-файл не локально, а на
серверах GitHub, бесплатно, через браузер.

### Что уже готово в этом архиве
Файл `.github/workflows/build.yml` — это инструкция для GitHub, которая
сама соберёт APK при каждой загрузке кода.

### Шаги:
1. Зарегистрируйся на https://github.com (бесплатно)
2. Создай новый репозиторий (кнопка "New repository")
3. Загрузи туда всю папку `MatchMVP` (на странице репозитория — кнопка
   "Add file → Upload files", можно перетащить папку целиком)
4. Перейди во вкладку **Actions** на странице репозитория — сборка
   запустится автоматически через минуту-две
5. Когда сборка завершится (зелёная галочка) — открой её и скачай
   готовый файл во вложениях (Artifacts) внизу страницы
6. Перенеси скачанный `.apk` на телефон и установи вручную (нужно будет
   разрешить "Установку из неизвестных источников" в настройках телефона —
   это нормально для собственных тестовых сборок, не для публикации)

### Честно про этот способ
Это рабочий, но "на голом энтузиазме" вариант — сборка Android-проектов
в облаке иногда требует донастройки под конкретный проект (несовпадение
версий Gradle/Java — самая частая причина, почему первая попытка не
срабатывает с первого раза). Если готовой сборки с первого раза не
получится — не значит, что что-то сломано непоправимо, обычно это
вопрос подгонки одной-двух версий в конфиге.

**Более надёжная (но не бесплатная навсегда) альтернатива для новичка** —
специализированные облачные сборщики именно под мобильные приложения,
например Codemagic или Appcircle: там меньше ручной настройки, они сами
подтягивают нужные версии Android SDK/Gradle, у обоих есть бесплatный
пробный период. Если облачная сборка через GitHub не заведётся с
первого раза — это более простой путь для человека без опыта.

## Как опубликовать в Google Play — подробная инструкция

### Шаг 1. Аккаунт разработчика
1. Зайди на https://play.google.com/console
2. Зарегистрируйся как разработчик — единоразовый платёж **$25**
3. Заполни данные (может потребоваться на юрлицо или физлицо, для России/СНГ — уточни актуальные ограничения Google Play на момент публикации, они периодически меняются)

### Шаг 2. Подготовь иконку и графику
Google Play требует минимум:
- Иконку приложения 512×512 px (PNG)
- Скриншоты минимум 2 штуки (реальные скриншоты с телефона)
- Баннер для магазина (feature graphic) 1024×500 px
- Короткое описание (до 80 символов) и полное описание приложения

### Шаг 3. Собери подписанный release-файл (.aab)
Google Play принимает только формат **.aab** (Android App Bundle), не .apk:

1. В Android Studio: `Build → Generate Signed Bundle / APK`
2. Выбери **Android App Bundle**
3. Создай новый ключ подписи (keystore) — **сохрани его в надёжном месте
   и никогда не теряй**: без него ты не сможешь выпускать обновления
   этого же приложения в будущем
4. Собери в режиме `release`

### Шаг 4. Заполни карточку приложения в Play Console
- Категория: Знакомства (Dating) — Google Play предъявляет к этой
  категории **повышенные требования модерации**, будь готов к более
  долгой проверке, чем для обычных приложений
- Возрастной рейтинг: обязательно укажи 18+ при заполнении анкеты
  контента — это отразится в опроснике IARC
- Политика конфиденциальности: **обязательна**, нужна ссылка на
  реальную страницу (можно сделать простую страницу на GitHub Pages
  или Google Sites) — без неё приложение не пройдёт модерацию

### Шаг 5. Data Safety (раздел о данных)
Google Play обязательно спросит, какие данные собирает приложение.
Для этого проекта честно указать:
- Собираем: номер телефона (для функции мэтчинга), примерное местоположение
  через Bluetooth-прокси (для функции "кто рядом")
- Не передаём третьим лицам
- Пользователь может удалить данные (стоит добавить такую функцию в
  приложение до публикации, Google Play всё чаще требует конкретную
  кнопку удаления аккаунта/данных, а не просто описание в тексте)

### Шаг 6. Внутреннее тестирование перед публичным релизом
**Настоятельно рекомендуется**, а не пропускать:
1. В Play Console создай трек **Internal Testing**
2. Загрузи туда .aab
3. Добавь email-адреса своих 2-3 тестеров
4. Проверьте на реальных телефонах, что Bluetooth-мэтчинг физически
   работает — это тот момент, где может понадобиться донастройка под
   конкретные модели устройств (BLE ведёт себя по-разному на разных чипсетах)

### Шаг 7. Отправка на модерацию
- После внутреннего теста — перевод в трек **Production**
- Модерация обычно занимает от нескольких часов до нескольких дней,
  но **приложения категории "Знакомства" и приложения, использующие
  Bluetooth/местоположение, проверяются строже и дольше** — закладывай
  запас по времени перед пилотным ивентом

### Честно о рисках модерации именно для этого приложения
Google Play особенно внимательно проверяет: (а) приложения категории
знакомств на предмет защиты несовершеннолетних — 18+ ценз должен быть
не просто заявлен, а по-настоящему реализован при регистрации;
(б) любые permission на Bluetooth/местоположение — модератор проверит,
действительно ли они используются по прямому назначению, а не для
слежки. Учитывая всю историю обсуждения этого проекта — архитектура
уже спроектирована с учётом этих требований, но будь готов, что
модератор может запросить дополнительные пояснения при первой подаче.

## Важные ограничения этой версии (честно)

- **Только Android.** Для iOS нужно отдельное приложение на Swift
  (CoreBluetooth) — техническая логика похожая, но код другой.
  Могу сделать следующим шагом.
- **Направления (стрелки) нет** — только факт "рядом" через список.
  Настоящее "теплее/холоднее" по силе сигнала можно добавить отдельно
  (см. `BleScanner.kt`, там уже прокинут RSSI, просто пока не используется
  на UI).
- **Не проверяет реальный возраст** — только честная галочка "мне 18+".
  Для настоящего запуска (не пилота с доверенными тестерами) нужна
  более серьёзная верификация.
- **Не протестировано на реальных устройствах мной** — код написан
  корректно по документации Android BLE API, но финальная проверка
  на живых телефонах — за тобой. Возможны мелкие доработки под
  конкретные модели телефонов (BLE ведёт себя по-разному на разных
  чипсетах, это нормально для этой технологии).
